# Qodana quality gate: Long Parameter List (BattleShip2)

O cheiro no código (*code smell*) escolhido foi **Long Parameter List**, do catálogo de Martin Fowler. Este cheiro ocorre quando um método recebe demasiados parâmetros, tornando a sua utilização, compreensão e manutenção mais difíceis.

Ferramenta utilizada: **Qodana for JVM Community** (`jetbrains/qodana-jvm-community:2026.2`), integrado no GitHub Actions.

## Ficheiros desta entrega

| Ficheiro | Localização |
|---|---|
| Workflow | `.github/workflows/qodana-smell-129830.yml` |
| Configuração do linter | `qodana-129830.yaml` |
| Perfil de inspeção | `.qodana/profiles/profile-129830.yaml` |

O workflow utiliza `JetBrains/qodana-action@v2026.2.2`, com JDK 21, e o linter identificou-se nos logs como **Qodana for JVM 2026.2.4**.

## Tabela de mapeamento (passo 4)

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar | Limitações |
|---|---|---|---|---|
| Long Parameter List | Java → Method metrics → Method with too many parameters | `ParametersPerMethod` | Número de parâmetros (`PAR`); `m_limit: 5` | Limiar absoluto, não relativo ao projeto. Não avalia a necessidade ou o significado dos parâmetros, nem assinala certos métodos que implementam ou sobrescrevem métodos de supertipos. |

O perfil ativa a inspeção `ParametersPerMethod` com limite de **5 parâmetros**. Assim, um método elegível com **6 ou mais parâmetros** é sinalizado.

## Relação com o livro e limiares utilizados

A ficha laboratorial apresenta *Long Parameter List* como cheiro detetável através da inspeção *Method with too many parameters*. O livro *Object-Oriented Metrics in Practice*, de Michele Lanza e Radu Marinescu, não fornece uma estratégia de deteção específica para este cheiro nas disharmonies dos capítulos 5–7. Por isso, foi utilizado o limiar absoluto de 5 parâmetros da inspeção do IntelliJ/Qodana, e não um valor atribuído ao livro.

Ao contrário das estratégias quantitativas do livro que combinam métricas e limiares relativos, esta configuração apenas compara o número de parâmetros com um valor fixo.

## Configuração do quality gate

No perfil de inspeção foi definida a seguinte regra:

```yaml
name: "Long Parameter List 129830"
baseProfile: empty
inspections:
  - inspection: ParametersPerMethod
    enabled: true
    severity: WARNING
    options:
      m_limit: 5
```

Na configuração `qodana-129830.yaml`, foi definido o quality gate:

```yaml
failureConditions:
  severityThresholds:
    any: 0
```

Deste modo, a existência de **pelo menos um problema** faz falhar o job. O valor `m_limit: 5` controla a deteção do cheiro, enquanto `severityThresholds.any: 0` controla quantos problemas são tolerados pelo gate. O workflow é executado em *pull requests*, em *pushes* para `main` e manualmente.

## Provocar o cheiro e corrigir (passo 9)

Foi introduzido deliberadamente um método de teste `method` na classe `AI`, no ficheiro `src/main/java/battleship/AI.java`, com **6 parâmetros inteiros**:

```java
void method(int a, int b, int c, int d, int e, int f) {
    // faz nada
}
```

O Qodana identificou **1 ocorrência** de *Method with too many parameters* e, como o limite do gate era zero, a execução falhou. Em seguida, foi retirado um parâmetro da assinatura do método, passando de 6 para **5 parâmetros**:

```java
void method(int a, int b, int c, int d, int e) {
    // faz nada
}
```

A alteração está documentada no commit [`f8bf394`](https://github.com/LEI-129850/Battleship2/commit/f8bf394471cd2264c07a10ca30e133d8b19eafaa). Na execução seguinte, o Qodana reportou **0 problemas** e o gate passou.

| Execução | Resultado | Problemas | Ligação |
|---|---|---:|---|
| Método com 6 parâmetros | **Falha** | 1 | [Execução 42513239383](https://github.com/LEI-129850/Battleship2/actions/runs/42513239383) |
| Método corrigido para 5 parâmetros | **Passa** | 0 | [Execução 42513706252](https://github.com/LEI-129850/Battleship2/actions/runs/42513706252) |

Os logs confirmam que, em ambos os casos, foi carregado o perfil **Long Parameter List 129830**. Os relatórios completos foram publicados como artefactos `qodana-report.zip` nas respetivas execuções.

## Proteção do ramo `main` (passo 10)

Foi criada uma regra de proteção (Rulesets) no ramo `main` que exige que o check `Qodana Long Parameter List 129830` do GitHub Actions passe antes do merge de um pull request. Com o gate vermelho, o botão de merge fica bloqueado.

## Reflexão

O Qodana detetou corretamente o método `AI.method` com seis parâmetros e fez falhar o quality gate; depois da remoção de um parâmetro, deixou de encontrar problemas e a execução passou. Neste teste não foram observados falsos positivos ou falsos negativos, mas a ferramenta pode sinalizar métodos cujos numerosos parâmetros são justificáveis e não avaliar todos os casos relevantes. A sensibilidade depende de `m_limit`: reduzir esse valor aumenta o número potencial de ocorrências, enquanto alterar `severityThresholds.any` apenas modifica a tolerância do gate. Face às estratégias apresentadas em *Object-Oriented Metrics in Practice*, esta abordagem é limitada por usar um limiar absoluto e por não avaliar as relações semânticas entre parâmetros nem combinar várias métricas.
