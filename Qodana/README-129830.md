## Objetivo

Detetar métodos com demasiados parâmetros e utilizar um quality gate
no GitHub Actions para sinalizar essas ocorrências.

Uma lista extensa de parâmetros pode dificultar a compreensão,
utilização e manutenção de um método.

## Tabela de mapeamento

| Cheiro | Inspeção no IDE | ID utilizado no linter | Métrica / limiar | Limitações |
|---|---|---|---|---|
| Long Parameter List | Java → Method metrics → Method with too many parameters | ParametersPerMethod | Número de parâmetros; máximo de 5, configurado por m_limit | Limiar absoluto. Não avalia a necessidade ou relação semântica entre os parâmetros. Métodos que sobrescrevem ou implementam métodos de supertipos não são reportados. |

O limite por omissão documentado é 5. Com esta configuração,
um método elegível com 6 ou mais parâmetros deve ser sinalizado.

A página do Inspectopedia apresenta MethodWithTooManyParameters
na secção de localização e ParametersPerMethod como Inspection ID.
O relatório produzido pelo linter utilizado neste projeto regista
a inspeção como ParametersPerMethod, pelo que esse é o identificador
adotado no perfil.

## Relação com a ficha e com o livro

Long Parameter List pertence ao catálogo de cheiros de Martin Fowler
e aparece na tabela de exemplos da ficha laboratorial.

O livro Object-Oriented Metrics in Practice não apresenta uma
estratégia própria para este cheiro entre as disharmonies dos
capítulos 5–7. O limite de 5 parâmetros provém da documentação
da inspeção e não é atribuído ao livro.

Esta abordagem utiliza uma contagem absoluta, não uma combinação
de métricas e condições lógicas como outras estratégias do livro.

O perfil utiliza o formato de ficheiro separado:

    name: "Long Parameter List 129830"
    baseProfile: empty
    inspections:
      - inspection: ParametersPerMethod
        enabled: true
        severity: WARNING
        options:
          m_limit: 5

A base empty permite ativar apenas a inspeção pretendida.
As verificações de configuração do Qodana, designadas sanity,
continuam ativas por omissão.

## Funcionamento do quality gate

O workflow executa em pull requests, em push para main
e manualmente através de workflow_dispatch.

A opção pr-mode: false solicita análise integral do projeto.

São utilizados dois limites diferentes:

- m_limit: 5 — máximo de parâmetros permitido por método.
- Limite do quality gate: 0 — máximo de problemas tolerado.

Na configuração utilizada, o gate está definido por:

    failureConditions:
      severityThresholds:
        any: 0

O gate falha quando existe pelo menos um problema contabilizado.
Alterar este limite não altera a sensibilidade da inspeção:
essa é controlada por m_limit.

## Validação da configuração

Durante a configuração, uma execução aplicou o perfil Default
e reportou 225 problemas de várias inspeções. Esses resultados
não correspondiam exclusivamente a Long Parameter List.

Após a alteração do formato do perfil, o relatório confirmou
o carregamento de Long Parameter List 129830, mas apresentou
zero ocorrências. A inspeção ParametersPerMethod estava desativada
no perfil gerado e apenas as verificações de sanity estavam ativas
no perfil efetivo.

Por isso, esse resultado de zero ocorrências não foi considerado
evidência de ausência do cheiro. O identificador do perfil foi
corrigido para ParametersPerMethod; a sua ativação e deteção
devem ser confirmadas na execução seguinte.
