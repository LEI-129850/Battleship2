A tabela da ficha indica que Feature Envy não tem uma inspeção equivalente.
Contudo, a documentação do Qodana for JVM 2026.2 identifica a inspeção
FeatureEnvy. Esta foi escolhida como aproximação, pois a sua heurística
não equivale à estratégia quantitativa do livro.

Foi utilizado o Qodana for JVM Ultimate; não se pressupõe que esta
inspeção esteja disponível no linter Community.

## Estratégia de deteção do livro

No livro Object-Oriented Metrics in Practice, secção 5.4, páginas 84–85,
a Figura 5.4 apresenta a seguinte estratégia, aplicada a métodos:

(ATFD > FEW) AND (LAA < 1/3) AND (FDP <= FEW)

- ATFD — Access To Foreign Data: quantidade de atributos externos
  distintos acedidos diretamente ou através de métodos de acesso.
- LAA — Locality of Attribute Accesses: proporção de acessos a
  atributos locais relativamente ao total considerado pela métrica.
- FDP — Foreign Data Providers: número de classes que fornecem
  os atributos externos acedidos.

A figura usa o limiar simbólico FEW. A tabela 2.4, página 18, apresenta
os valores e rótulos semânticos usados para estes limiares.

## Aproximação com Qodana

A inspeção FeatureEnvy identifica métodos com três ou mais chamadas
a métodos de outra classe, respeitando as exclusões da inspeção.

Esta abordagem não permite reproduzir diretamente:

- A contagem de atributos externos distintos exigida por ATFD.
- A condição LAA < 1/3.
- A condição FDP <= FEW.
- A conjunção das três condições para o mesmo método.

Não foram encontradas opções documentadas para configurar estas
métricas ou alterar o limiar interno da inspeção. Por isso, não foram
incluídas opções não confirmadas no perfil YAML.

ser indicada em `projectJDK`.

O linter Ultimate exige um token de projeto configurado no secret
`QODANA_TOKEN` do repositório.

O perfil ativa a inspeção FeatureEnvy com severidade WARNING.
As inspeções de diagnóstico da configuração, qodana.sanity,
continuam ativas por omissão.

O quality gate utiliza:

    failureConditions:
      severityThresholds:
        any: 0

Assim, qualquer problema contabilizado pelo gate provoca uma falha.
Este valor controla o número de problemas tolerados, não o número
de chamadas necessário para identificar Feature Envy.

O workflow executa em push para main, em pull requests e manualmente.
A opção `pr-mode: false` solicita uma análise integral, sem limitar
a análise aos ficheiros alterados no pull request.
