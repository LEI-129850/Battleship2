## Objetivo

Identificar métodos com demasiados parâmetros e integrar essa
verificação no GitHub Actions através de um quality gate.

Uma lista extensa de parâmetros pode dificultar a compreensão
e utilização de um método e indicar a necessidade de refatorização.

## Tabela de mapeamento

| Cheiro | Inspeção no IDE | ID para configuração | Métrica / limiar | Limitações |
|---|---|---|---|---|
| Long Parameter List | Java → Method metrics → Method with too many parameters | MethodWithTooManyParameters | Número de parâmetros; máximo de 5, configurado por m_limit | Limiar absoluto. Não avalia a relação semântica entre parâmetros. Métodos que sobrescrevem ou implementam métodos de supertipos não são reportados. |

O valor 5 é o limite por omissão documentado da inspeção.
Com esta configuração, um método elegível com 6 ou mais parâmetros
deve ser reportado.

## Relação com a ficha e com o livro

Long Parameter List pertence ao catálogo de cheiros de Martin Fowler
e aparece na tabela de exemplos da ficha laboratorial.

O livro Object-Oriented Metrics in Practice não apresenta uma
estratégia própria para este cheiro entre as disharmonies dos
capítulos 5–7. Assim, não se atribui ao livro o limite de 5 parâmetros:
este provém da documentação da inspeção do Qodana.

A abordagem utilizada é uma regra quantitativa simples, baseada
num limite absoluto, e não uma combinação de métricas relativas
ao sistema.

## Funcionamento do quality gate

O workflow executa:

- Em pull requests.
- Em push para main.
- Manualmente, através de workflow_dispatch.

A opção pr-mode: false solicita análise integral, incluindo
os ficheiros que não foram alterados pelo pull request.

São utilizados dois limites distintos:

- m_limit: 5 — máximo de parâmetros permitido por método.
- failThreshold: 0 — máximo de problemas tolerado pelo gate.

O gate falha quando existe pelo menos um problema contabilizado.
Pode, portanto, falhar devido a ocorrências anteriores no projeto
ou a problemas de configuração, além do cheiro introduzido no teste.
