# Qodana: Acoplamento

Quality gate com o Qodana for JVM (Community) no GitHub Actions, para detetar instâncias do cheiro **Inappropriate Intimacy** (catálogo de Fowler) no projeto BattleShip2.

## 1. Tabela de mapeamento

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar | Limitações |
|---|---|---|---|---|
| High Coupling | *Overly coupled class* (Java, Class metrics); *Overly coupled method* (Java, Method metrics) | `ClassCoupling`; `MethodCoupling` | Nº de classes distintas referenciadas. Opções `m_limit` configuradas: **14** na classe e **7** no método. | Conta referências a classes, não a "intimidade" (acesso a membros privados, dependência bidirecional). Limiar absoluto, sem combinar CINT, CDISP e MAXNESTING como no livro. |

Opções usadas em ambas as inspeções: `m_includeJavaClasses: false` e `m_includeLibraryClasses: false` para garantir que apenas as dependências internas do próprio projeto são contabilizadas.

## 4. Reflexão

No BattleShip2, o quality gate com `ClassCoupling` e `MethodCoupling` (limiares ajustados para **14** na classe e **7** no método) assinalou as zonas mais centrais do código, nomeadamente o método construído para o efeito, bem como eventuais classes de orquestração.

Durante a análise, foi possível identificar **falsos positivos**: classes como a `Main` ou a `Game` atuam como orquestradoras e referenciam naturalmente muitas outras classes do domínio (ex: instanciar todos os tipos de navios, posições e tabuleiro). Este acoplamento elevado é uma necessidade arquitetural (Padrão Façade/Controlador) e não representa obrigatoriamente uma violação de *Inappropriate Intimacy*.

Por construção, existem também **falsos negativos**: no caso do método, cada classe referenciada conta apenas uma vez. Isto significa que um método que chame 15 métodos diferentes de uma única classe parceira regista apenas 1 dependência. Este cenário é o exemplo clássico de *Inappropriate Intimacy*, mas a inspeção do Qodana é incapaz de o sinalizar.

O resultado mostrou-se altamente **sensível ao valor-limite** (secção 3): ao reduzir o limite (ex: para 7/14), o linter começou a apanhar classes estruturais saudáveis, gerando ruído indesejado. Ao elevar os limites para valores mais tolerantes (ex: 15/20), os alertas desapareceram por completo, correndo-se o risco de ignorar anomalias reais no crescimento do acoplamento.

Face às estratégias de *Intensive Coupling* e *Dispersed Coupling* de Lanza e Marinescu, o Qodana permite apenas um limiar absoluto por inspeção: não combina condições lógicas (`AND`/`OR`), não calcula o rácio `CDISP = FANOUT / CINT` nem filtra por `MAXNESTING > 1`. Adicionalmente, conta classes referenciadas (uma aproximação a FANOUT) e não os métodos distintos chamados (CINT), pelo que a implementação deste gate é apenas uma aproximação superficial da métrica proposta no livro.
